# 协作与工作流

一刻已完成首轮原型 Demo 到 Flutter 的迁移，迁移成果获用户认可。当前开发围绕 Flutter 的产品、工程和运行体验推进。日常工作依据本地文档和 Dart 代码，不阅读原型、Vue 源码或调用 ProtoBridge MCP。阶段决策见 [Flutter 独立迭代](decisions/2026-10-23-flutter-development.md)。

## 开始工作

先读根 [README](../README.md)、[文档索引](README.md) 与 [已知缺口](known-gaps.md)，检查工作区已有改动。随后按任务阅读相关产品、交互、动效或工程规范及真实调用点，不要求每次阅读全部文档。

本仓库只维护一刻应用。保留无关的未提交内容；不修改 Producer、不复制 Evidence Store，不因普通 Flutter 任务重新采集或同步外部原型。

| 任务 | 阅读与验证入口 |

| 明确要求的 DS 同步 | DS Target Sync Skill；源文件仅在该专项范围读取 |

本地产品文档规定目标行为；Flutter 代码与已知缺口说明实现程度；测试、设备操作和性能测量证明各自覆盖的结果。历史原型与 receipt 用于追溯，不是日常产品需求的裁决来源。

文档未覆盖的工程细节由 Agent 结合架构和 Flutter 实践决定并验证；涉及业务后果、导航职责、新能力或产品风格的取舍，提出具体建议与影响后交由用户决定。动效意图不足时直接与用户讨论，不回读 Vue 寻找答案。

## 授权与实施

用户明确要求先评估或制定计划时，完成只读核对，提供具体方案、预计文件与验证方式。用户批准后持续完成约定范围，不为同一范围的文件修改、修复、测试或后续批次重复确认。

普通实施请求按任务范围直接执行。遇到尚未决定的产品问题或超出授权的变更，只暂停依赖该决定的部分，继续完成独立工作。已批准的体验决策及时写入 [决策记录](README.md#决策记录)，并更新所属产品规范，避免再次成为待决事项。

只有用户明确要求新原型迁移、固定 Evidence 核对、还原验收或 DS 同步时才进入专项流程；提供历史 Handoff ID、修改公共组件或普通动效调试本身不触发专项。已批准专项范围的实施授权持续有效，Skill 不增加重复批准要求。

## 验证与交付

普通任务运行独立客户端入口 `node tool/verify.mjs`，按变更补充必要原生验证。文档可单独运行 `node tool/check-docs.mjs`。外部 DS 检查是显式专项入口，不是普通客户端检查的依赖；专项采用的检查失败须如实处理或报告，不静默忽略。

分别报告代码检查、行为测试、原生目视和性能测量。截图不能证明动画过程，模拟器不能证明真机性能，历史成功不能替代本次检查。交付说明最终行为、主要文件、验证结果和仍未覆盖的边界。

产品变化更新对应规范；工程边界更新工程文档；未完成能力和待决事项更新已知缺口。历史评审保留当时范围及结论，仅修正维护中的链接。固定 Evidence 专项的固定引用、风险与五维报告要求见 [专项文档](integrations/proto-bridge.md#专项流程与交付)。

## 文档维护与引用

产品、体验与工程规则在本仓库自足维护；普通开发不通过相邻仓库路径或本机绝对路径跳转阅读。Markdown 链接使用仓库内的相对路径，目录调整时同时更新链接、锚点、Skill 与机器索引。生成目录不承载规范。

优先在所属本地文档说明本项目需要的规则，避免把关键依据交给外部文档或易变分支。确有不可替代的外部说明时使用 GitHub 固定提交的文件链接并说明用途，不链接本机外仓文件或 GitHub 分支。当前维护文档无需外链。历史附件路径可作为追溯文字或保存在原 receipt，不作为当前可用链接，也不证明本次已核验。

`node tool/check-docs.mjs` 检查所有非生成 Markdown 的文件目标、锚点与仓库边界；即使相邻仓库恰好存在，越界链接也会失败。动效规格描述已批准的目标；实际完成度以已知缺口和最近交接记录为准，不把设计规格当作完成声明。
